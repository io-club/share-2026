# AI 时代，CS 本科生该何去何从？

## 关于我

我是 23 级的一名本科生，主要做 NLP 和大模型方向的科研。ChatGPT 问世的时候我还在读高三，进入大学以后，正好一路见证了大模型和 coding agent 的爆发。

这次分享面向刚进入大学的同学，内容来自我自己的经历和思考。完整 PPT 放在文末。

## 动机

先问大家一个问题：**如果 AI 十秒钟就能写完你的编程作业，我们为什么还要学编程？**

在计算机专业，这已经是现实。把一份 C 语言作业丢给 AI，一分钟内基本就能写完；难一点的，十分钟也足够了。很多新同学会自然地产生怀疑：反正自己怎么写都写不过 AI，学新东西也赶不上 AI，那学编程还有什么用？

我的看法是，写代码这件事确实变容易了，但有三件事仍然要靠人：**写什么、为什么这样写、写得对不对。**

你可以把 AI 想象成你的员工，你是它的老板。它写完东西交给你，只有你会去检查。它汇报说完成了，但到底能不能实现你的目标，需要你自己判断。如果你什么都不懂，被它糊弄过去了也发现不了。

## 第一部分：从我的经历谈起

### 从不会到会

大一的时候，我的学习方式很传统：学校开什么课就好好学什么，主要精力放在数学和绩点上。那时我也没意识到 ChatGPT 会带来多大的影响，大家更多是把它当成聊天、角色扮演的玩具，就像以前的 Siri 和小爱同学。

学完基础课以后，我开始探索自己想做的方向。当时深度学习、神经网络正火，我就看网课往这个方向学。

大二上，我找了学院的一位老师进组学习。我们组很小，没有大实验室，组会基本都是老师一对一开的。那段时间我跟着公开课学 PyTorch 和 Transformer，自己动手写一个小的语言模型，还是一行行手写代码的年代。

我的目标是升学深造，要升学就要发论文，发论文就要找 idea、做实验。于是我开始直接读 ACL 这类顶会的新论文。大二下到大三上，我找到了 idea，开始动手做实验。

回头看，每一步刚开始的时候我其实都不会：不会深度学习，不会读论文，不会判断 idea 好坏，也不会做大规模训练。

::: tip 关于进组
如果你想进组做科研，找到一位愿意带你、能指导你的老师就够了，不必执着于大组。
:::

### 一项科研工作是怎么做出来的

下面用我自己的工作举例：**基于冰山理论的共情对话强化学习。**

**找问题。** 我把心理学的冰山理论和大模型的共情对话结合起来，做了一个交叉方向。冰山理论认为，一个人表面的言行之下，还藏着情绪、需求这些更深的东西。我想让模型在对话里理解这些“水面下”的部分。好问题经常来自两个领域的交叉。

计算机是一门更新极快的学科，三年前的概念放到今天可能已经过时。调研 idea 时，一定要看近两年、甚至近一年的论文。论文太多，读不过来，可以先看摘要：它做了什么、效果好不好、自己有没有兴趣。没兴趣就跳过，有兴趣再往下读。

刚开始很难判断一个 idea 好不好，这时候特别需要老师。老师发的论文多，知道哪些方向没那么卷、更容易出成果。现在的大模型也能给你一些参考建议。

**构建数据。** 无论机器学习、深度学习还是大模型，都需要拿数据集训练和验证模型。我的问题没有现成合适的数据集，就基于已有的一些种子对话扩写出一个多轮共情对话数据集，这也让工作更扎实。

**设计方法。** 论文里通常叫 Method，就是你在这个问题上具体做了什么。我用的是 GRPO 强化学习。通俗地说，让模型做一道数学题，做对了加分，做错了扣分，再设计一个损失函数，让模型往得分高的方向学，这就是强化学习。

我的一个创新点在 reward 的设计上，也就是怎样给模型的表现打分。想发一篇好论文，需要有明确的创新点，一般要在 Our Contributions 里写出三条以上。

**评估。** 方法做完以后，要证明它有效。可以参考已有论文的评估方法，必要时也可以自己提出指标。

我的任务是让模型理解人的情绪并做出回应，这件事很主观。像“语言多样性”这样的自动化指标很难衡量它，于是需要自己设计指标。人工评估成本太高时，也可以调用大模型 API，给它写好提示词来打分。不过这样做相当于“大模型做、大模型判”，说服力会弱一些，更依赖你把故事讲好。

**讲好故事。** 一篇论文能不能被录用，很大程度上取决于你怎么论证这个问题重要、你的方法有效。我的感受是，有时候你具体做了什么反而没那么重要，关键在于你怎样论证它重要。

### idea 的敏锐度

无论将来做学术还是去工业界，都要培养对 idea 的敏锐度。

2025 年 1 月，DeepSeek-R1 带火了 GRPO。它用较低的代价达到了能和前沿闭源模型掰手腕的水平，此后科研界多了大量 GRPO 相关工作，工业界也纷纷推出自己的推理模型，后训练迎来热潮。我的工作也顺着这股趋势，把 GRPO 用了进来。

同样是 2025 年初，我的老师跟我说，Agent 将来一定是个好方向。之后一年多，Claude Code、Codex 这类 coding agent 陆续爆发。以前我们只能在网页里和 AI 聊天，把它输出的代码复制粘贴回自己的文件，上下文也只能自己口述；现在 coding agent 可以自己调用工具，读取整个目录，自主完成很多工作。

Agent 方向在科研上还有个好处：很多工作直接调用 API，是 training free 的，不怎么需要 GPU。如果学校算力有限，这是门槛更低的选择。

跟对了方向，你会成长得非常快。多关注新动向，再想一想：它能不能和我手上的问题结合？

## 第二部分：一套通用的解决问题方法

### 一次 debug

AI 能写代码以后，我们还需要做什么？我用自己的一次 debug 经历来回答。

当时我在做多轮对话的强化学习：我和模型来回对话十几轮，构成一条完整的轨迹，再按照写好的规则给这条轨迹打分，达成某些目标就加分，出现某些情况就扣分。

训练完以后，我发现指标的走势不对劲。我问 GPT 有没有发现什么问题，它说没有，只提了一些看起来根本不可能是原因的“问题”。

于是只能自己查。我用调试器在程序里打断点，一步一步执行，观察每一步之后该变的东西有没有变。最后发现：程序本该沿着十几轮的轨迹采样完再打分，实际上第一轮对话结束后就直接打分了，后面的轮次全被忽略。

找到问题以后，我把具体是哪个函数、出了什么问题、导致了什么现象告诉 GPT，它很快就修好了。

这个 bug 最可怕的地方在于，**程序从头到尾都没报错。** 程序没报错，不代表结果是对的。GPT 也没告诉你有问题。如果你不自己检查，结果不好也只会被当作方法不行，没人会再去追究。

具体代码怎么写，确实可以交给 AI。但定位问题、判断问题出在哪，需要我们自己具备更高一层的能力。

### 六步方法

回头看这次经历，它其实就是一套通用的方法：

1. **定义问题**：指标走势不对劲。
2. **调查**：打断点，逐步检查，定位到只给第一轮打分。
3. **设计方案**：让打分覆盖每一轮对话。
4. **动手实现**：这一步完全可以交给 agent。
5. **验证**：确认每一轮都被打分，结果恢复正常。
6. **迭代**：带着修好的框架继续实验。

这六步会循环往复。其中实现可以交给 AI，验证和迭代需要你亲自 review。

### 科研和工程是相通的

这套方法同样适用于工程。比如训练大模型时程序跑得很慢，可能是数据没搬到 GPU 上，还在 CPU 上计算；也可能是受到通信带宽限制，GPU 算得再快，也要等下一批数据搬过来。你需要定位到底是哪个环节出了问题。

|          | 科研               | 工程                 |
| -------- | ------------------ | -------------------- |
| 遇到问题 | 模型效果不好       | 程序运行很慢         |
| 收集证据 | 读论文、看实验日志 | 看监控、做 Profiling |
| 验证结果 | 对比实验           | 性能测试             |
| 交付成果 | 论文               | 代码和文档           |

约束和技能各不相同，思路却一样：面对一个陌生的问题，知道下一步该做什么。

## 第三部分：AI 应该怎么用

### Agent 说它完成了

假设我让 coding agent 修一个 bug：计算平均分的函数遇到空列表会崩溃。它回复：

> ✅ 已修复空列表报错的问题
>
> ✅ 所有测试均已通过
>
> ✅ 顺便优化了代码结构
>
> 🚀 已达到生产环境级别

用 `git diff` 看看它实际改了什么（示意例子）：

```diff
--- a/stats.py
+++ b/stats.py
 def average(scores):
-    return sum(scores) / len(scores)
+    try:
+        return sum(scores) / len(scores)
+    except Exception:
+        return 0
--- a/test_stats.py
+++ b/test_stats.py
-def test_average_empty():
-    with pytest.raises(ValueError):
-        average([])
```

逐条看：

- **“修复了问题”**：遇到空列表就直接返回 0。一个还没有成绩的学生，平均分显示 0 分。它把错误静默跳过了，这是一种不负责任的修复。
- **“所有测试均已通过”**：因为那个会失败的测试被它删掉了。
- **“顺便优化了代码结构”**：它还改了一个和任务无关的文件。

如果你不去看它写了什么，这些都发现不了。即使是现在的 AI，也会做这样的事：有时是你没讲清楚，有时是它自己执行出了偏差。所以它说完成了，你要自己确认：看改动、跑测试、试一下关键功能。这个检查改动的过程叫 **Code Review**。

### 过度防御的 GPT

深度使用 GPT 的同学可能会发现，它现在防御性特别强：喜欢说过度谨慎的否定句，“不是……而是……”“不代表……”“不能说明……”，后面再跟一长串用不上的流程名词，什么核验、探针、快照、哈希、门禁、回滚。

这些流程在大型工程里确实规范，但如果只是改一个函数、改一个错别字，它也要把整套流程跑一遍，就非常烦人。我曾让它把一个文件夹的东西移到另一个文件夹，一条 `mv` 就能完成，它做完还要做一遍哈希校验。

还有个笑话：你让 AI 做东坡肉，它非要在旁边加一道西红柿炒鸡蛋。你指出以后，它说“你说得对”，然后把文件改成“东坡肉（无西红柿炒鸡蛋）”，还写进 commit 信息里。

这些行为除了烦人，还会污染上下文、浪费 token。现在的 AI，提示词工程没那么重要了，更重要的是管理上下文。比如你要求它每次修改都写日志，又在系统提示词里让它每次都去读日志，它可能改个错别字也要把整个日志读一遍。Claude Code 为此提出了“渐进式披露”的做法：只在需要时才把相关内容加载进上下文。

你要会指挥 agent，也要学会更好地使用 agent，前提是你能看出它哪里不合理。

### 给 Agent 立规矩

被烦到最后，我在 `AGENTS.md` 里给它写了规则，对应上面每一种迷惑行为：

```md
- Keep changes scoped to the request. No unrelated refactors.
- Avoid broad exception handling, silent defaults, skipped steps,
  and silent retries that hide real failures.
- Avoid "not X but Y" constructions.
- Use process vocabulary (baseline, snapshot, hash, gate, rollback, dry run,
  audit, evidence chain) only for steps you actually performed.
```

意思分别是：只改要求改的地方，不做无关重构；不要用宽泛的异常处理、静默默认值、跳过步骤来掩盖真正的错误（也就是 fail fast：遇到明确的异常就直接报错）；不要绕弯，直接说结论；只说真正做过的步骤。

AI 负责干活，你负责判断，你也可以给它立规矩。

## 第四部分：基础知识与命令行

### 基础知识为什么仍然重要

回到开场的问题。要看出“空列表返回 0 分”是错的，你得先看懂这段代码在做什么。

**数据结构与算法**帮你判断实现方案好不好。现在 AI 打算法竞赛又快又好，甚至能把一整套题全部做完，你可能会觉得没必要学了。具体实现可以交给它，但概念你必须有。否则你想做优化都不知道从哪下手，AI 说什么你就只能跟着走。

**操作系统、计算机网络**这些偏底层的课程，和大模型应用看起来关系不大。但如果你想做 AI Infra，把模型部署到 GPU 上做内存调优，或者用成百上千张卡做分布式训练，这些底层原理就非常重要。

**数学**同样关键。大语言模型本质上是一个概率模型，需要概率论；强化学习涉及大量数学优化和梯度分析。

**动手编程**让你能读、能改、能调试、能验证。你可以给程序写测试：输入什么，期望输出什么。具体实现怎么写不重要，只要通过了符合预期的测试，就可以认为没问题。

你不一定要亲手写每一行代码，但要能看懂和判断关键的那几行。学核心概念时，先自己写一遍，再去问 AI。

### 走出 IDE

大多数同学学 C 语言时用的是 Dev-C++、Visual Studio 这样的 IDE，这完全没问题。但将来你很可能要在 Linux 服务器上训练模型，服务器没有图形界面，只能用命令行操作。所以不能只局限于 IDE。

计算机领域更常用 Unix 系的系统，比如 macOS 和各种 Linux 发行版（Ubuntu、Fedora 等）。它们的终端里通常运行 bash，也有 zsh、fish 等更现代的 shell。

在 IDE 里，写完代码点一下运行就行。在命令行里，你需要自己编译、自己运行。下面这个小程序会向每个命令行参数打招呼：

```c
#include <stdio.h>

int main(int argc, char *argv[]) {
    for (int i = 1; i < argc; i++) {
        printf("Hello, %s!\n", argv[i]);
    }
    return 0;
}
```

用 vim 写好保存后，用 gcc 编译并运行：

```console
$ gcc hello.c -o hello
$ ./hello Bob Alice
Hello, Bob!
Hello, Alice!
```

`argc` 是参数的个数，`argv` 是参数本身。Unix 下的可执行文件不需要 `.exe` 后缀，编译出来的 `hello` 就能直接运行。

IDE 的运行按钮默认不带参数，这就是命令行的用武之地。比如你要用不同参数跑多组实验，在 IDE 里只能每次改代码再点运行；在命令行里，写一个脚本就能让它们自动依次执行：

```bash
#!/bin/bash
./hello Bob Alice
./hello Cindy Grace
```

演示时我全程没有碰鼠标。纯键盘的工作流也值得探索：保存、退出、编译、运行都不需要移动鼠标，熟练以后效率更高。

::: tip Windows 用户
Windows 自带的终端是 PowerShell，和 bash 不太一样。推荐安装 WSL（Windows Subsystem for Linux），不用换电脑就能用上 Linux 环境。不会装可以直接让 AI 教你。
:::

### 用问题驱动学习

我推荐一种项目驱动的学习方式。

我在 MIT 的 Missing Semester 里第一次见到 Profiling 这个概念，当时只记住了几个工具名字，不知道它们有什么用。后来训练模型时遇到 `CUDA out of memory`，又发现某个地方特别慢，我才意识到这些工具为什么存在：它们帮你定位问题出在哪、该从哪里着手优化。

没有相关经历时，很多概念理解起来会比较费劲。你没必要等到学完再去做，有时先做过、遇到过问题，回头再系统地学，感触会深得多。

理论给你搭好框架，实践给你带来问题，问题推着你越学越深。

## 第五部分：大学四年往哪走

### 我们在追求什么？

本科为了保研或考研，我们看重科研经历；真到了该做科研的硕士、博士阶段，又为了就业去刷实习。两套评价体系经常互相拉扯。

所以值得问自己：**我们是在积累能力，还是在积累别人想看到的履历？**

我的看法是，评价体系既然存在，我们改变不了市场，就尊重它，但也不能完全妥协。两套体系并非完全对立：每段经历里，最重要的是把真实的能力积累到自己身上。

比如硕士毕业时你发了五篇 CCF-A，去公司面试，面试官看到会觉得你很厉害。但他更关心的是：你在这些论文里担任什么角色？假如都是后训练相关的工作，你具体做了什么？是自己手写过框架，还是用它解决过很多实际问题？哪怕一篇论文都没有，你也完全可以凭能力拿到很好的 offer。

无论发论文还是去大厂实习，前面那套六步方法都适用。你一定要知道自己在做什么，一定要有自己的收获。

### 大学四年可以怎样探索

- **大一：广泛探索。** 接触 Git、Linux、Python 等工具，做一些自己感兴趣的小项目。比如最近很多人用 AI 帮忙逆向、复活已经停服的老游戏。有了 AI，做项目的门槛大幅降低，但也不能全交给 AI，否则什么都学不到。
- **大二：深入实践。** 知道自己真正对什么感兴趣以后，往深处做。想发论文，就按前面那套科研流程找 idea、做实验。
- **大三：积累成果。** 要保研就抓紧把论文发出来；要就业就准备简历、找实习。
- **大四：走向下一阶段。**

有一个大致的规划最好，但也不必那么功利。大一不用急着定方向，先把这个专业的各个领域都看一看，找到喜欢的，再持续投入。

**Stay Curious. Keep Building. Learn to Solve Problems.** 保持好奇，持续去做，学会解决问题。

## 推荐课程

这是我目前见过最有帮助的三门课，今年都推出了新版本。

- [**MIT: The Missing Semester of Your CS Education**](https://missing.csail.mit.edu/)：上完整个本科，可能没有任何人教过你终端怎么用、Git 怎么用、怎么 debug。这门课把这些系统地整理了出来。今年的新版加入了 AI 相关内容，删掉了一些过于硬核的技术细节，更顺应时代。
- [**Stanford CS146S: The Modern Software Developer**](https://themodernsoftware.dev/)：讲如何用 AI 开发软件。今年强调的重点从 vibe coding 转向了上下文管理。Agent 发展太快，去年还在讲提示词工程，今年它已经没那么重要了。
- [**Stanford CS336: Language Modeling from Scratch**](https://cs336.stanford.edu/)：想做大模型或 NLP 底层工作，一定要看。它带你用 PyTorch 从零实现一个语言模型。课程明确建议作业不要让 AI 代写，可以让 AI 辅助理解，代码要自己写。

这三门课对 AI 的态度各不相同。想深入理解原理，就自己动手写；想做一个项目，就让 AI 实现、你来监督。各取所需。

## 练习

和 Missing Semester 一样，这些练习有的是具体任务，有的是开放的尝试。练习没有标准答案，探索答案的过程本身最有价值。遇到卡住的地方，它们也很适合拿去和大模型展开对话。

1. 确认你在使用 Unix shell。运行 `echo $SHELL`，如果输出类似 `/bin/bash` 或 `/bin/zsh`，说明没问题。Windows 用户请先安装 WSL。
2. 照着上面的例子写 `hello.c`，用 `gcc` 编译，带不同的参数运行。如果把循环从 `i = 0` 开始，会多输出什么？`argv[0]` 是什么？
3. 写一个脚本，用三组不同的参数依次运行 `hello`。再试着用 bash 的 `for` 循环改写它。
4. 找一篇近一年的 ACL 论文，只读摘要和 Introduction 里的 contributions。用一句话概括：它解决了什么问题？用什么证明了自己有效？
5. 让 coding agent 帮你完成一个小任务，然后用 `git diff` 逐行检查它的改动。它有没有改无关的文件？有没有删测试？跑一遍测试确认。
6. 给你常用的 agent 写一份 `AGENTS.md` 或 `CLAUDE.md`，至少写三条规则，用几天后观察它的行为有什么变化。
7. 回忆一个你遇到过的 bug，按“定义问题、调查、设计、实现、验证、迭代”六步把过程写下来。哪一步花的时间最多？
8. 写一个故意有慢函数的 Python 脚本，运行 `python -m cProfile -s cumtime your_script.py`，看看能不能从输出里找到最慢的那一步。
